ЧАСТЬ 1. КОНЦЕПЦИЯ: ЗАЧЕМ МУЛЬТИ-АГЕНТНАЯ СИСТЕМА

1.1. Что такое "AI-агент" — честное определение
--------------------------------------------------

В индустрии слово "агент" используется расплывчато. В нашем контексте
агент — это:

  - Один большой языковой модели (LLM) вызов,
  - С персональным system prompt'ом (инструкцией кем быть),
  - Имеющий доступ к набору инструментов (читать файлы, искать в базе,
    дёргать API),
  - Работающий в цикле "подумал → вызвал инструмент → получил результат
    → подумал снова" до решения задачи.

Главное отличие от обычного чата: агент САМ решает, какие шаги предпринять,
а не ждёт твоего следующего сообщения после каждого действия.

Это всё. Никакой магии. Под капотом — те же модели (Claude, GPT, Gemini),
но обёрнутые в цикл и снабжённые ролью + инструментами.


1.2. Зачем разделять на много агентов
--------------------------------------------------

Можно сделать ОДНОГО большого агента с гигантским system prompt'ом, где
описать все 8 ролей сразу. Это будет работать. Но плохо.

Причины разделения:

  (а) Фокус контекста. У каждой модели есть "контекстное окно" — количество
      токенов, которые она держит в голове. Чем больше всякого там лежит,
      тем хуже она фокусируется на текущей задаче. Узкий агент = чище фокус.

  (б) Раздельная отладка. Если Discovery Lead плохо квалифицирует — ты
      правишь промпт ТОЛЬКО его, не трогая остальное. С одним мега-агентом
      каждая правка может сломать другие роли (это называется
      "regression" — регрессия качества).

  (в) Раздельная модель. Разным ролям нужны разные модели. Solution Architect
      требует глубокого reasoning'а (Claude Opus / GPT-5). Proposal Writer —
      стилистики (Claude Sonnet). Effort Estimator — точности на цифрах
      (GPT-5 с включённым reasoning). Раздельные агенты = раздельные модели.

  (г) Раздельные эвалы. "Эвал" (evaluation) — это набор тестов: "вот вход,
      вот ожидаемый выход". У каждого агента — свой эвал. Прогнал —
      понял, не сломал ли его. Без разделения эвалы невозможны.

  (д) Психологическая ясность. Тебе самому легче работать с системой,
      где явно понятно: эту задачу решает Х, а эту — Y.


1.3. Что такое супер-агент (orchestrator)
--------------------------------------------------

Супер-агент — это агент, который НЕ решает задачу сам, а:

  - Принимает запрос пользователя,
  - Решает, какие из специализированных агентов нужны и в каком порядке,
  - Передаёт им задачи и собирает их результаты,
  - Возвращает финальный ответ пользователю.

По сути — менеджер проекта в виде LLM.

В академической литературе это называется "orchestrator-worker pattern"
или "supervisor pattern". См. Anthropic 2025 paper "Building Effective
Agents" — там это разобрано подробно.

ВАЖНОЕ ОГРАНИЧЕНИЕ В НАШЕМ СТЕКЕ:
GitHub Copilot в VS Code НЕ умеет автоматически передавать задачи между
агентами. Это его архитектурное ограничение. Мы это обойдём через
гибридный подход: Director-агент составляет план + передаёт контекст
через файлы, а пользователь руками переключается между ролями. Это
реалистичный мульти-агент в Copilot-стеке.

Когда упрёшься в потолок этого подхода — переедешь на Claude Code,
CrewAI или свой MCP-сервер. Но первые 2-3 месяца hybrid вполне работает.


1.4. Когда мульти-агент стоит, а когда — нет
--------------------------------------------------

СТОИТ, если:
  - Задача имеет несколько чётко различимых этапов (как пре-сейлс)
  - Этапы требуют разной экспертизы
  - Между этапами есть передача артефактов (discovery → blueprint → proposal)
  - Ты планируешь регулярно использовать систему (не один раз)

НЕ СТОИТ, если:
  - Задача одношаговая ("переведи этот документ")
  - Ты используешь раз в месяц (overhead не окупится)
  - У тебя нет времени поддерживать (агенты деградируют без обновления)

2.1. Три инструмента — кто чем занимается
--------------------------------------------------

GITHUB:
  - Хранилище файлов агентов (system prompt'ы, скиллы, шаблоны)
  - Версионирование (видно, что менялось)
  - Бэкап (если ноут умрёт — всё на серверах GitHub)
  - В корпоративной версии — приватность гарантирована
  - НЕ участвует в runtime работы агентов. Это просто хранение.

VS CODE:
  - Твоё единственное рабочее место
  - Здесь ты открываешь папку проекта как workspace
  - Здесь же — Copilot Chat (через расширение GitHub Copilot)
  - Здесь же — терминал для git push/pull
  - В Enterprise редакции — единственный санкционированный
    способ дотянуться до Copilot. Веб-интерфейс github.com/copilot
    и CLI заблокированы IT-политикой.

COPILOT:
  - Это шлюз (gateway) к моделям. По сути — одна корп. подписка дает
    доступ к Claude Sonnet 4.5, GPT-5, Gemini 2.5 Pro и другим
    frontier-моделям через один интерфейс.
  - Поддерживает Custom Instructions, Chatmodes, Prompt Files,
    MCP servers — это и есть механизмы кастомизации.
  - Тарификация в "premium requests" — см. часть 3.

2.3. Как это работает в одной фразе
--------------------------------------------------

Файлы агентов лежат в папке. VS Code эту папку показывает. Copilot эти
файлы читает как контекст. Ты в чате выбираешь модель и chatmode
(агента) и общаешься. GitHub — только архив.

ЧАСТЬ 3. ПОНЯТИЯ GITHUB COPILOT, КОТОРЫЕ НУЖНО ЗНАТЬ

3.1. Premium requests — как тарифицируется
--------------------------------------------------

Copilot НЕ считает токены как Anthropic/OpenAI API. С июня 2025 он
перешёл на модель "premium requests" — запросов к "умным" моделям.

Что бесплатно:
  - Inline-подсказки (автокомплит в редакторе) на базовой модели
  - Чат на базовой модели (GPT-4.1) — безлимит

Что списывает premium requests:
  - Любой запрос к Claude Sonnet/Opus, GPT-5, Gemini 2.5 Pro
  - Agent Mode (когда Copilot сам ходит по файлам)
  - Каждый запрос = 1 request × multiplier модели
    (Sonnet 4.5 = 1×, Opus 4 = 10×, GPT-5 = 1×)

Лимиты:
  Free        — 50/мес
  Pro         — 300/мес ($10)
  Pro+        — 1500/мес ($39)
  Business    — 300/seat ($19)
  Enterprise  — 1000/seat ($39)

ВАЖНО для твоего проекта:
Твои 8 кастомных chatmodes НЕ тратят токены отдельно. Каждый чат с
агентом = 1 premium request, ровно как обычный чат. Кастомизация
бесплатна.

Где смотреть расход:
  github.com → Settings → Copilot → Usage


3.2. Inline completions vs Chat vs Agent mode
--------------------------------------------------

Это ТРИ РАЗНЫХ режима работы Copilot, важно не путать.

INLINE COMPLETIONS:
  - Подсказки прямо в редакторе по Tab
  - Идут только по коду и тексту в файле
  - Используют базовую модель, безлимит
  - Для наших агентов — НЕ актуально, это для разработки

CHAT:
  - Боковая панель в VS Code (Ctrl+Alt+I)
  - Здесь ты общаешься с агентами
  - Выбираешь модель и chatmode из выпадашек
  - ОДИН запрос = ОДИН ответ. После ответа цикл прерывается, ждёт тебя.

AGENT MODE (в Chat есть тоггл "Agent"):
  - Copilot сам решает: прочитать файл, запустить команду, изменить код
  - Работает в цикле, пока не решит задачу или не упрётся
  - Расходует premium requests на каждом шаге
  - Полезно для: автогенерации файлов, многошаговых задач

В нашем проекте используем CHAT с переключением chatmodes. Agent Mode
полезен для тяжёлых задач (типа сгенерируй blueprint по brief).


3.3. Четыре механизма кастомизации Copilot
--------------------------------------------------

Это ключевая часть. Все наши агенты живут именно здесь.

(А) CUSTOM INSTRUCTIONS — .github/copilot-instructions.md
    - Файл в корне репо. Copilot читает АВТОМАТИЧЕСКИ на каждый запрос
      в этом workspace.
    - Аналог CLAUDE.md или AGENTS.md.
    - Сюда кладёшь: общий контекст проекта, конвенции, язык ответов,
      правила безопасности.
    - НЕ зависит от выбранного chatmode — действует всегда.

(Б) CHATMODES — .github/chatmodes/*.chatmode.md
    - Каждый файл = одна персона агента.
    - YAML-заголовок (description, tools) + Markdown-тело (system prompt).
    - В чате появляется выпадашка "Mode" — выбираешь нужного.
    - ЭТО И ЕСТЬ ТВОИ АГЕНТЫ. 8 chatmodes = 8 агентов.

(В) PROMPT FILES — .github/prompts/*.prompt.md
    - Переиспользуемые промпт-команды.
    - Вызываются через /имя-промпта в чате.
    - Удобно для повторяющихся задач:
        /parse-rfp        → агент парсит RFP-документ
        /estimate-effort  → агент оценивает трудозатраты
        /build-blueprint  → агент собирает solution blueprint
    - Работают поверх ЛЮБОГО chatmode'а.

(Г) MCP SERVERS — .vscode/mcp.json
    - Внешние коннекторы (Confluence, Jira, SharePoint, БД, своя CRM)
    - Дают агентам инструменты типа search_confluence_kb(query)
    - Настраиваются один раз — доступны всем chatmodes
    - Это enterprise-уровень. На MVP не нужно.


3.4. Пример chatmode-файла
--------------------------------------------------

Файл: .github/chatmodes/solution-architect.chatmode.md

  ---
  description: SAP Solution Architect для пре-сейлс HANA трансформаций
  tools: ['codebase', 'search', 'fetch']
  ---
  Ты — Senior SAP Solution Architect с 15+ лет опыта в S/4HANA, BTP,
  RISE with SAP. Твоя задача — на основе discovery-документа от
  Discovery Lead собрать solution blueprint для HANA трансформации.

  ВСЕГДА:
  - Сверяйся с knowledge/sap-products/ перед утверждениями о модулях
  - Используй шаблон templates/solution-blueprint/
  - Указывай явно: scope, out-of-scope, assumptions, risks
  - Различай Greenfield, Brownfield, Selective Data Transition подходы
  - Отвечай по-русски

  НЕ ДЕЛАЙ:
  - Не оценивай трудозатраты (это Effort Estimator)
  - Не пиши коммерческое предложение (это Proposal Writer)
  - Не отвечай на вопросы вне твоей роли — перенаправляй к Director'у

  ВХОД: discovery-output.md или brief от пользователя
  ВЫХОД: working/blueprint-{дата}.md по шаблону

4.2. Логика: где живёт супер-агент
--------------------------------------------------

Файл director.md в корне репо.

ПОЧЕМУ в корне, а не в agents/_director/:
  - Это привычное место для главного инструктажа (как README или CLAUDE.md)
  - Copilot первым делом видит файлы корня
  - Психологически: открыл проект — сразу видно главный мозг

Содержимое director.md:
  - Кто есть кто среди 8 агентов
  - Какую роль вызывать в каких ситуациях
  - Какие flows доступны
  - Правила передачи контекста (через файлы в working/)
  - Чек-листы: что должно быть готово на каждом этапе


4.3. Личные скиллы агента vs общие
--------------------------------------------------

ЛИЧНЫЕ (agents/{role}/skills/):
  - Применимы только к этой роли
  - Discovery Lead: stakeholder-mapping, bant-qualification, pain-points
  - Solution Architect: module-selection, integration-mapping,
    landscape-design
  - Live в той же папке, что и сам агент — легче поддерживать вместе

ОБЩИЕ (skills/):
  - Нужны нескольким агентам
  - parse-rfp, search-knowledge, translate-ru-en, format-document
  - Когда замечаешь "о, этот скилл нужен и Discovery, и Architect, и
    Proposal Writer" — переноси в общие.

ПРАВИЛО ПЕРЕНОСА: если 3+ агента используют один скилл — он общий.
Меньше — оставь локально.


4.4. Что такое "knowledge/" и зачем
--------------------------------------------------

Это твоя БАЗА ЗНАНИЙ. Сюда складываешь:
  - knowledge/sap-products/  — доки по S/4HANA, BTP, Datasphere, BW/4HANA
  - knowledge/case-studies/  — анонимизированные прошлые кейсы
  - knowledge/pricing-guides/ — прайс-листы, методики ценообразования
  - knowledge/industries/    — отраслевая специфика (retail, banking,
                                manufacturing)

На MVP-этапе агенты читают эти файлы НАПРЯМУЮ как контекст (Copilot
поддерживает #file: или просто упоминание имени файла).

Когда knowledge/ распухнет > 50 файлов или > 100 МБ — Copilot
перестанет справляться с прямым чтением. Тогда нужен RAG (см. 4.5).


4.5. RAG — что это и когда нужен
--------------------------------------------------

RAG = Retrieval-Augmented Generation. Расшифровывается так:

  - Retrieval — поиск релевантных кусков знания
  - Augmented — обогащение запроса найденными кусками
  - Generation — генерация ответа моделью

Как работает технически:
  1. Все документы из knowledge/ разбиваются на куски (chunks) по 500-2000
     токенов.
  2. Каждый кусок прогоняется через embedding-модель — превращается в
     вектор (массив из 1500 чисел, описывающий смысл).
  3. Векторы хранятся в векторной БД (Chroma, Pinecone, Vectara).
  4. Когда агент задаёт вопрос — вопрос тоже превращается в вектор.
  5. Векторная БД находит топ-5 самых "близких" по смыслу кусков знаний.
  6. Эти куски подсовываются модели как контекст к ответу.

Когда нужен RAG:
  - knowledge/ > 50 файлов
  - Документы > 50 МБ суммарно
  - Поиск по точному совпадению уже не работает (нужен семантический)

Когда НЕ нужен:
  - На MVP-этапе. 5-10 ключевых файлов — Copilot прочитает напрямую.

Способы добавить RAG в наш стек:
  (а) Copilot Spaces — загружаешь файлы, Copilot сам делает поиск.
      Простой, но данные у Microsoft (для корп. конфиденциальной
      инфы может не пустить EPAM Security).
  (б) MCP-сервер с локальным Chroma — векторная БД на твоём диске,
      MCP даёт агентам tool search_knowledge. Сложнее, но приватно.
  (в) Vectara / Pinecone через MCP — облачный векторный поиск,
      нужно согласовать с Security.


4.6. Что такое "connectors/" и MCP
--------------------------------------------------

MCP = Model Context Protocol. Открытый стандарт от Anthropic
(декабрь 2024), сейчас поддерживается Copilot, Claude, Cursor.

Что это: способ давать LLM-агентам ДОСТУП к внешним системам через
стандартный интерфейс. Раньше каждая интеграция писалась отдельно —
теперь есть единый протокол.

Как работает:
  - MCP-сервер — это маленькое приложение (Python/TypeScript), которое
    знает, как ходить в одну конкретную систему (Confluence, Jira,
    PostgreSQL).
  - Он экспортирует "инструменты" (tools) типа:
        search_confluence_kb(query: string) → результаты
        get_jira_ticket(id: string) → детали тикета
  - В Copilot ты прописываешь в .vscode/mcp.json: "вот сервер
    confluence-kb, он на таком-то порту, у него такие tools".
  - Дальше любой агент в Copilot может вызвать эти tools.

В нашем проекте connectors/ — это место, где ХРАНИТСЯ КОНФИГ
коннекторов (не сам код). Сам MCP-сервер может быть запущен:
  - Локально (npx @smithery/cli install @epam/confluence-mcp)
  - На внутреннем EPAM-сервере
  - В Docker-контейнере

В EPAM скорее всего уже есть готовый MCP-сервер для KB. Уточни у
EPAM AI team или DevOps.

7.1. Автоматизация презентаций (PowerPoint)
--------------------------------------------------

Цель: чтобы агент сам собирал черновик презентации по blueprint'у.

ВАЖНО: нативного "редактирования PPT через Copilot" в нашем стеке нет.
Есть три рабочих пути:

(А) Генерация через Markdown → конвертация
    - Агент пишет презентацию в .md (по слайдам через ---)
    - Конвертер типа Marp / Pandoc → .pptx
    - Просто, бесплатно, но шаблоны простые.

(Б) python-pptx через MCP
    - Пишешь маленький MCP-сервер: tool create_presentation(title,
      slides[]).
    - Под капотом python-pptx собирает .pptx по корп. шаблону EPAM.
    - Сложнее, но даёт твой брендинг.

(В) Microsoft 365 Copilot
    - Отдельная подписка от GitHub Copilot.
    - Если есть в EPAM — Copilot в PowerPoint умеет генерить и редактировать
      слайды по описанию.
    - Самый "wow", но платный отдельно.

Рекомендация: начни с (А), если упрёшься в брендинг — перейди на (Б).


7.2. Confluence KB через MCP

Цель: агенты могут искать в EPAM KB без копирования файлов локально.

Шаги:
(1) Узнаёшь у EPAM IT / AI team: есть ли уже одобренный MCP-сервер

(2) Если нет — поднимаешь @aaronsb/confluence-cloud-mcp или
    @atlassian/mcp-atlassian (open-source).
(3) Регистрируешься: создаёшь API-токен в личном Atlassian.
(4) В .vscode/mcp.json прописываешь endpoint и credentials

(5) В chatmodes добавляешь в tools: ['search_confluence'] — теперь

7.3. Настоящий RAG (когда knowledge/ распух)
--------------------------------------------------

Признаки, что пора:
  - В knowledge/ > 50 файлов
  - Размер > 100 МБ
  - Поиск по упоминанию имени файла перестал давать ответ —
    нужно искать по смыслу

Минимальный путь:
(1) Устанавливаешь Chroma локально (Python, pip install chromadb)
(2) Пишешь скрипт index_knowledge.py — обходит knowledge/, режет

(3) Поднимаешь MCP-сервер chroma-mcp, который даёт tool
    search_knowledge(query)
(4) Прописываешь в .vscode/mcp.json
(5) Все агенты теперь видят инструмент search_knowledge

ЧАСТЬ 9. АНТИПАТТЕРНЫ — ЧЕГО НЕ ДЕЛАТЬ
================================================================================

9.1. "Один агент на всё"
Соблазн: сделать одного супер-разумного агента с промптом на 5 страниц.
Реальность: фокус размывается, агент путается, отлаживать невозможно.
Правило: 1 агент = 1 чёткая роль = промпт на 1-2 страницы.

9.2. "Сначала наполню всё, потом запущу"
Соблазн: сначала заполнить knowledge/ 200 файлами, прописать 8 агентов,
3 коннектора — и потом проверить.
Реальность: половина окажется ненужной, агенты будут "не туда".
Правило: запускай на реальной задаче после первых 3 агентов. Дальше —
расширяешь по факту.

9.3. "Скопируй мега-промпт с интернета"
Соблазн: найти "лучший промпт для Solution Architect 2025" и поставить
у себя.
Реальность: чужой промпт не знает твоего контекста (EPAM, EU клиенты,
SAP HANA специфика).
Правило: чужие промпты — как референс, но свой пиши под свою практику.

9.4. "Сразу подключим Confluence + Jira + SharePoint"
Соблазн: с MVP сразу врубить все коннекторы.
Реальность: каждый коннектор — это 0.5-2 дня настройки + согласование
Security. На MVP застрянешь на коннекторах, до агентов не дойдёшь.
Правило: коннекторы во ВТОРОЙ месяц. На MVP — файлы напрямую.

9.5. "Будет работать само"
Соблазн: один раз настроил — работает вечно.
Реальность: SAP-доки обновляются, EPAM-практики меняются, новые
кейсы появляются. Без апдейта раз в месяц система устаревает.
Правило: запланируй 2 часа в неделю на review и улучшения.

9.6. "Конфиденциальные данные клиента в knowledge/"
Соблазн: сложить туда настоящие RFP клиентов, контакты, цифры.
Реальность: репо может стать доступен (даже приватный — у IT есть
доступ).
Правило: только АНОНИМИЗИРОВАННЫЕ примеры. Имена → "Client A".
Цифры → диапазоны.

9.7. "Доверяй и не проверяй"
Соблазн: получил blueprint от агента → сразу клиенту.
Реальность: LLM галлюцинируют. Особенно на цифрах и SAP-модулях.
Правило: всё, что идёт клиенту, ты прочитал сам. Агент — черновик,
не финал.

ЧАСТЬ 10. ГЛОССАРИЙ
================================================================================

AGENT (агент)
  LLM с system prompt'ом + инструментами, работающий в цикле "подумал —
  вызвал tool — получил результат — подумал".

AGENT MODE
  Режим Copilot, где он сам выполняет многошаговые задачи (читает
  файлы, правит, запускает команды).

BANT
  Фреймворк квалификации лида: Budget, Authority, Need, Timeline.

BROWNFIELD
  Подход к SAP-трансформации: апгрейд существующей ECC до S/4HANA
  с сохранением кастомизаций. Противоположно Greenfield.

CHATMODE
  Файл в .github/chatmodes/, описывающий персону агента в Copilot.

CONTEXT WINDOW (контекстное окно)
  Сколько токенов модель держит в "оперативке". Для Claude Sonnet 4.5 —
  200K, для GPT-5 — 400K. Превысил — модель забывает старое.

CUSTOM INSTRUCTIONS
  Файл .github/copilot-instructions.md, читаемый Copilot на каждый
  запрос. Глобальный инструктаж.

EMBEDDING
  Превращение текста в вектор (массив чисел), описывающий смысл. Нужно
  для семантического поиска (RAG).

EVAL (evaluation)
  Набор тестовых кейсов для агента: вход → ожидаемый выход.

FLOW
  Готовый сценарий: какие агенты в каком порядке используются под
  типовую задачу.

GREENFIELD
  Подход к SAP-трансформации: внедрение S/4HANA "с нуля", без переноса
  кастомизаций. Противоположно Brownfield.

HALLUCINATION (галлюцинация)
  Когда LLM уверенно выдумывает факты, которых нет. Главная причина,
  почему нужно проверять выходы агентов.

LLM
  Large Language Model. Модель типа Claude, GPT, Gemini.

MCP (Model Context Protocol)
  Открытый стандарт от Anthropic для подключения внешних инструментов
  к LLM-агентам.

ORCHESTRATOR (оркестратор)
  Супер-агент, который координирует работу других агентов.

PREMIUM REQUEST
  Единица тарификации Copilot для запросов к "умным" моделям.

PROMPT FILE
  Файл .github/prompts/*.prompt.md, переиспользуемая промпт-команда,
  вызывается через /имя.

RAG (Retrieval-Augmented Generation)
  Подход, где перед генерацией ответа модель получает релевантные куски
  из векторной БД.

S/4HANA
  Современная ERP-платформа SAP, заменяет ECC. Может работать только
  на in-memory БД HANA.

SELECTIVE DATA TRANSITION
  Третий подход к SAP-трансформации (помимо Greenfield/Brownfield):
  переносится только нужная часть данных и процессов.

SYSTEM PROMPT
  Главная инструкция модели — кто она, как себя вести, что НЕ делать.

TOKEN (токен)
  Минимальная единица текста, с которой работает LLM. Примерно
  4 символа = 1 токен для русского, 0.75 слова = 1 токен для английского.

TOOL (инструмент)
  Функция, которую агент может вызвать: read_file, search_knowledge,
  create_pptx и т.д.

VECTOR DATABASE (векторная БД)
  БД, хранящая embedding'и и умеющая искать "близкие по смыслу" вектора.
  Примеры: Chroma, Pinecone, Vectara.

WORKSPACE
  Открытая в VS Code папка, видимая Copilot как контекст.


================================================================================
ЗАКЛЮЧЕНИЕ
================================================================================

Главные идеи в одном абзаце:
Мульти-агентная система — это набор узкоспециализированных LLM-вызовов
с разными ролями + супер-агент-дирижёр + общая база знаний + механизмы
передачи контекста между ними. В стеке "Enterprise GitHub + Copilot +
VS Code" это реализуется через chatmodes (агенты), Custom Instructions
(глобальный инструктаж), prompt files (переиспользуемые команды) и
MCP-серверы (коннекторы). За 4 часа можно собрать MVP с 3 агентами на
реальной задаче. За день — полный вариант с 8 агентами, шаблонами,
flows и knowledge base. Дальше — расширение через RAG, Confluence KB,
автоматизацию презентаций — но только после того, как базовая система
работает и понятны узкие места.

Главные правила:
  1. Узкие агенты лучше широких.
  2. Запускай на реальной задаче после 3 агентов, не после 8.
  3. Один коммит = одно улучшение одного агента.
  4. Эвалы важнее красивых промптов.
  5. Никакой конфиденциальной инфы в репо.
  6. Агент = черновик, человек = финал.

Удачи. И помни — это инструмент твоего усиления, а не замены. Лучший
pre-sales — тот, кто использует AI, но думает сам.
