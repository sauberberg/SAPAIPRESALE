# Skill: Format Document

**Используется**: Proposal Writer, Demo Engineer, Compliance Reviewer
**Когда**: Нужно привести документ в чистый, профессиональный вид перед отправкой клиенту

## Что делает

Применяет EPAM presentation standards к Markdown-документу.

## Правила форматирования

### 1. Структура

✅ Каждый раздел нумерован: `## 1. Title`, `### 1.1 Subtitle`
✅ Не более 3 уровней вложенности (`#`, `##`, `###`)
✅ TOC (table of contents) для документов > 5 страниц

### 2. Стиль

✅ Активный залог: "Мы внедрим" не "Будет внедрено"
✅ Client-centric: "ваши процессы" не "наш продукт"
✅ Конкретика: цифры, метрики, сроки
❌ Канцеляризмы: убирать "осуществлять", "производить", "реализовывать"
❌ Маркетинговый bullshit: "лучший в мире", "уникальный подход"

### 3. Списки vs таблицы

- **Списки** — для последовательных шагов / однородных пунктов (5-7 максимум)
- **Таблицы** — для сравнения / структурированных данных

Чем 8+ пунктов списком, тем лучше таблица с категорией.

### 4. Числа и единицы

✅ "12 месяцев" не "12 м."
✅ "EUR 850,000" не "850K EUR"
✅ "30-70 ЧД" не "примерно 50 ЧД"
✅ Диапазон лучше точки на pre-sales стадии

### 5. SAP-термины

✅ S/4HANA — capital S, slash, capital HANA
✅ BTP (полностью SAP Business Technology Platform на первом упоминании)
✅ Fiori (без курсива, без кавычек)
✅ S/4HANA Cloud Private vs S/4HANA Cloud Public — разделять явно

❌ S4 HANA, S4/HANA, S4Hana — все неправильно

### 6. Языковая чистота

Русский документ:
- SAP-термины — английские, без транслита ("BTP" не "БТП")
- Цифры — латинские (1, 2, 3)
- Кавычки — «ёлочки» в русском тексте
- Знаки — тире (—) для пауз, дефис (-) для составных

Английский документ:
- US English by default (color, not colour)
- Если клиент UK — UK English consistently

### 7. Финальный чек-лист

- [ ] Нет TODO, TBD, XXX placeholders
- [ ] Все имена/цифры подставлены
- [ ] Версии SAP-продуктов проверены
- [ ] Контакты EPAM правильные
- [ ] Confidentiality footer на каждой странице
- [ ] Spell check прогнан
- [ ] Документ читается ВСЛУХ без запинок
